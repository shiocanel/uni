## Profilul companiei și contextul *Safety*

**Betfair Romania Development** este cel mai mare hub tehnologic al **Flutter Entertainment** (compania-mamă), având peste 2000 de angajați. Flutter Entertainment operează branduri mari de pariuri și jocuri online (FanDuel, PokerStars, Sportsbet, Betfair, Paddy Power, Sky Betting & Gaming etc.) pentru ~18 milioane de clienți la nivel global. Deviza echipei locale accentuează crearea de experiențe „captivante și sigure” pentru utilizatori. Postarea indică faptul că internul va lucra într-o **echipă front-end Safety**, orientată pe produs. Echipa *Safety* (atât online, cât și în centrul dedicat de la Leeds) se ocupă de **joaca responsabilă** („Responsible Gambling”): monitorizează tiparele de pariere, protejează segmente vulnerabile (minori, risc de dependență), impune limite voluntare (self-exclusion) și alerte pentru comportamente de risc. În plus, „safety” poate include **moderare de conținut** (chat-uri, forumuri) în platformă, pentru a evita abuzul, frauda sau limbajul ofensator. Soluțiile moderne (incluzând AI/ML) sunt tot mai folosite: inteligența artificială poate detecta semne timpurii de joc problemă și trimite alerte personalizate jucătorului (ex: notificări “unu dintre obiceiurile tale de pariere a depășit media”). ML/AI ajută astfel să reducă monitorizarea manuală și să ofere intervenții în timp real. Menționarea în anunț a "AI-oriented mindset" sugerează că echipa *Safety* e deschisă la tehnologii AI/ML pentru analiza datelor de joc și moderare.

## Tehnologii cheie de studiat

Pentru pregătire, trebuie revizuite conceptele și instrumentele solicitate (și câteva adiționale). Mai jos sunt temele principale, cu explicații și resurse de referință.

- **Front-end (Web și mobil)** – *JavaScript/TypeScript și framework UI*. Postul menționează React (sau alt framework JS) şi TypeScript. Așadar, cunoașterea ECMAScript modern, JSX/TSX și a unui framework component-oriented este esențială. Dacă se dorește, poate fi util și studiul Flutter (framework Google, limbaj Dart) – însă **atenție**: în contextul acestui rol „Flutter” se referă la companie, nu la SDK. Dacă nu se lucrează direct la aplicații mobile, cunoștințele Flutter sunt *nespecificate* în ofertă; totuși, pentru un interviu Full-Stack ar fi bine să cunoașteți diferențele Flutter vs. React (tabel comparativ mai jos). Flutter (Dart) permite crearea rapidă de UI native cross-platform (Android/iOS) cu *hot-reload* şi widgeturi UI bogate. React Native (JavaScript) folosește _bridge_ pentru componente native. Un bun exercițiu: creați o mică aplicație Flutter de tip counter sau listă preluată de la un backend. Cod de exemplu în Flutter (Dart):

  ```dart
  class CounterPage extends StatefulWidget {
    @override
    _CounterPageState createState() => _CounterPageState();
  }

  class _CounterPageState extends State<CounterPage> {
    int _count = 0;
    @override
    Widget build(BuildContext context) {
      return Scaffold(
        appBar: AppBar(title: Text('Contor')),
        body: Center(
          child: ElevatedButton(
            onPressed: () { setState(() { _count++; }); },
            child: Text('Apasă de $_count ori'),
          ),
        ),
      );
    }
  }
  ```
  *Resurse*: Documentația oficială Flutter (tutorial „Get started”), codelaburi și exemple Google, precum și cursuri video. Pentru React/TS, tutoriale precum oficialul reactjs.org și TypeScript Handbook.

   *Exemplu de arhitectură stratificată Flutter: layer-ul Framework (Dart) comun cu librării UI (Material/Cupertino), Engine (C++) şi Embedder (platform-specific). Flutter compilează aplicațiile în cod nativ pentru performanță maximă.*

- **Back-end Java (Spring Boot/JPA)** – În rolul Full-Stack, partea server va fi în Java (Spring Boot). Arhitectura tipică: aplicație Spring Boot care expune API (REST sau GraphQL) și lucrează cu baza de date (MySQL). *ORM*: Spring Data JPA (Hibernate) este folosit pentru maparea obiect-relatională. De exemplu, un `@Entity` Java și un `JpaRepository` simplu pot realiza accesul în DB:

  ```java
  @Entity 
  public class Product {
      @Id @GeneratedValue(strategy=GenerationType.IDENTITY)
      private Long id;
      private String name;
      // ...
  }
  public interface ProductRepository extends JpaRepository<Product, Long> {
      List<Product> findByNameContaining(String name);
  }
  ```
  Documentația Spring Guide arată pas-cu-pas crearea unei aplicații cu Spring Data JPA. Studiu recomandat: tutoriale Spring oficiale (de ex. *Accessing Data with JPA*) și cursuri practice (ex. crearea unui serviciu CRUD în Spring Boot cu MySQL). De asemenea, Spring Security (pentru autentificare/autorizații) merită studiat: în mod uzual se folosesc protocoale precum OAuth2/JWT pentru protejarea API-urilor.

- **API (REST vs GraphQL)** – Cel mai probabil, serverul Java expune API REST tradițional (JSON). **REST** presupune endpoint-uri de tip `/resource` pentru diverse operații. **GraphQL** este alternativă care permite clientului să specifice exact ce date vrea (evitând _overfetching_/_underfetching_). Dacă anunțul nu spune clar dacă folosesc GraphQL, e bine să înțelegi ambele concepte. De exemplu, cu GraphQL  o singură interogare poate înlocui apeluri multiple REST. Comparativ:
  - *REST*: interfețe fixe pe resurse (ex: `/users`, `/orders`), necesită mai multe cereri, fixă schema răspunsurilor.
  - *GraphQL*: un singur endpoint `/graphql`, clienții cer exact câmpurile necesare într-o query, flexibil și evolutiv pentru front-end.
  
   *GraphQL permite specificarea exactă a datelor necesare în query, eliminând supra/subluarea de date care apare în REST. Exemplu: cu GraphQL, clientul definește câmpurile dorite, serverul răspunde cu exact acele date.*

- **Baze de date SQL (MySQL)** – În back-end se va folosi probabil o bază de date relațională (MySQL). Relația Java–DB se poate face cu JDBC/Spring Data. Practică curentă: scheme normalizate și interogări SQL cu JOIN, GROUP BY, tranzacții ACID. Exemplu de query SQL:
  ```sql
  SELECT u.name, COUNT(o.id) AS total_orders
  FROM users u
  JOIN orders o ON o.user_id = u.id
  WHERE u.active = 1
  GROUP BY u.name;
  ```
  Conform definițiilor, bazele SQL folosesc tabele și scheme fixe, ideale pentru date structurate și interogări complexe (JOIN). Prin contrast, NoSQL (ex. MongoDB) oferă scheme flexibile, scalare orizontală. Tabel comparativ mai jos. Se recomandă recitirea SQL, sintaxei JOIN, normalizare, indexuri, și un pic de NoSQL din curiozitate (dar focus pe SQL/MySQL pentru acest rol). 

- **ORM (Spring Data JPA)** – Cadru Java care leagă entități Java de tabele SQL. Spring Data JPA simplifică operațiile CRUD prin interface-uri (ex. `JpaRepository`) fără SQL explicit. Studiu: crearea entităților (annotate cu `@Entity`, `@Id`, etc) și repository-uri Spring. Exemple oficiale: [30] prezintă cum „Spring Data JPA stochează și recuperează obiecte într-o DB relațională”. Este util să exersezi operațiuni CRUD prin JPA (findAll(), save(), query method).

- **Autentificare/Autorizație** – Chiar dacă nu e explicit menționat în cerințe, majoritatea proiectelor enterprise implică securitate: protocoale OAuth2, token-uri JWT, autentificare bazată pe roluri. Din postare reiese că aplicațiile ar putea folosi AWS (identity services) și Kafka (mesaje securizate). În zona Full-Stack, trebuie să înțelegeți conceptele de sesiune, cookie-uri vs token-uri, plus posibile cadre folosite (Spring Security, Keycloak, Auth0 etc.). Notă: nu s-a specificat exact, deci studiați *conceptual* OAuth2 (Flow-urile Authorization Code, Implicit) și JWT (JSON Web Tokens) ca standarde curente.

- **Controale de calitate (CI/CD și testare)** – Se cere cunoștințe despre CI/CD și testing automată. *CI/CD* înseamnă fluxuri automate care compilează, testează și livrează codul. De exemplu, un pipeline simplu poate include: la commit – build + unit tests, apoi deploy automat în staging, teste de integrare, și în final deploy în producție. Graficul de mai jos arată componentelor cheie (Commit→Build→Test→Staging→Prod):

   *Stadii tipice într-un pipeline CI/CD: codul este comis, declanșează build-ul, testele rulează, produsul (artifactul) ajunge în stagiu și apoi în producție.*

  *(Imagine: Exemplu schematic al unui pipeline CI/CD; detaliu în sursa GitLab CI/CD.)*

  În practică, explorarea concretă: înțelegeți instrumente ca Jenkins, GitLab CI/GitHub Actions, și conceptele de pipeline (build artifact, medii de testare, containere Docker). 

- **Testare (unit/integration)** – Abilitatea de a scrie teste automate este esențială. Pentru Java, alegeți cel puțin JUnit (teste unitare) şi poate Mockito (mockuri) pentru backend. Pentru front-end JS/TS, puteți studia testare cu Jest/Mocha sau testare end-to-end cu Cypress. Pentru Flutter există `flutter_test`. Exercițiu: scrieți un test JUnit simplu pentru metoda unui service sau un widget test Flutter care verifică UI. 

- **Containere și Virtualizare** – Docker: cunoașteți noțiuni de bază despre containere: creare fișier `Dockerfile`, construire imagine, rulare container. Practică: containerizarea unui mic serviciu Spring Boot conectat la MySQL (sau un alt microserviciu). Multe implementări enterprise rulează microservicii în containere orchestrate (Kubernetes). Exercițiu: “Dockerize” un simplu API Java și un client web (sau chiar un API GraphQL cu Node.js), legate printr-o rețea Docker.

- **Cloud (AWS/Azure/GCP)** – În anunț apare AWS ca exemplu de cloud. Nu sunt detalii despre ce servicii AWS se folosesc, dar bazele generale sunt necesare. Studiați concepte de *compute* (EC2 vs serverless Lambda), *stocare* (S3 vs Azure Blob vs GCS), *baze de date* gestionate (RDS, Aurora), *CI/CD* cloud (CodePipeline, Azure DevOps), și *identitate/siguranță*. Cunoștințe despre un provider major (AWS de exemplu) sunt de ajuns; conceptele sunt similare și la Azure/GCP. Exemple: auto-scalare EC2, deploy aplicații pe Elastic Beanstalk, sau serverless functions. O listă de comparație între AWS/Azure/GCP poate fi utilă. Resurse: tutoriale AWS Essentials, certificări gen AWS Certified Cloud Practitioner (sit oficial AWS).

### Comparativ tehnologii

| Tehnologie / caracteristică | Avantaje (exemple) | Dezavantaje / Când se evită |
|---|---|---|
| **Flutter (Dart)** | Cross-platform mobil & web, *hot-reload* rapid, performanță nativă ridicată (cod compilat ARM), ecosistem Google, UI bogat (widget-uri Material/Cupertino) | Comunitatea mai mică decât React, fișiere executabile mai mari, Dart mai puțin cunoscut la început |
| **React Native (JS/TypeScript)** | Dezvoltare cross-platform mobil cu JavaScript/TS, comunitate mare, reutilizare de skill-uri web (React) | Performanță inferioară (bridge JS↔native) față de Flutter, pot exista probleme de compatibilitate între versiuni și debugging mai dificil |
| **REST API** | Model simplu bazat pe resurse URL, foarte răspândit, caching bine susținut HTTP, control ușor al versiunii API | Overfetching/Underfetching de date (aplicații trebuie de multe ori să facă mai multe cereri); rigid când frontend-ul evoluează |
| **GraphQL API** | Un singur endpoint, clientul cere exact câmpurile dorite, ideal pentru aplicații frontend complexe/evolutive, flexibilitate mare, analize fine pe interogări | Suprasarcină de configurare (schema+resolvers), posibil încărcare ineficientă la abuz (complexitatea query-urilor), caching mai complex de implementat |
| **SQL (MySQL)** | Tabele relaționale, tranzacții ACID, interogări complexe cu JOIN, şiret schema, maturitate în scenarii comerciale | Scalare verticală limitată (poate necesita replici/clusterizare), schema fixă (dificil de schimbat frecvent) |
| **NoSQL (MongoDB/Cassandra)** | Scheme flexibile (documente/cheie-valoare), scalare orizontală ridicată, ideal pentru date semi-structurate sau volume mari | Nu suportă bine tranzacții complexe (ACID limitat), lipsa de JOIN-uri sau relații complicate, consistență eventuală (CAP) |
| **CI/CD (Jenkins/GitLab/GitHub)** | Automatizează build-test-deploy, detectează erori rapid, permite livrare continuă fără downtime; popular în DevOps | Cerință inițială de configurare, mentenanță continuă a scripturilor de pipeline, încărcare inițială a învățării (înțelegerea tuturor pașilor) |

## Claude (Anthropic) și LLM-uri în fluxul de siguranță

**Claude** este o serie de modele lingvistice mari (**LLM**) dezvoltate de compania **Anthropic**. Lansat în 2023 ca chatbot AI, Claude poate genera și interpreta text, răspunde întrebărilor și scrie cod. Spre exemplu, *Claude 4 Opus* este un model avansat orientat pe cod și conversații. Compania pune accent pe *Constitutional AI* (antrenare pentru siguranță) pentru a reduce output-ul nociv.

În contextul „safety”, LLM-urile precum Claude pot fi integrate în fluxurile de moderare și prevenire a abuzurilor. De exemplu, ele pot analiza automat conținutul generat de utilizatori (mesaje din chat, recenzii) pentru a detecta limbaj ofensator, auto-vătămare, înşelătorii, limbaj de ură etc. Modelele de tip LLM sunt bune la **interpretarea nuanțelor limbajului** și la clasificarea conținutului conform politicilor de siguranță. Astfel, Claude poate fi folosit pentru a însoți sau filtra conținutul înainte de expunerea către public: *classifyaza textul în categorii („aprobat”, „flagged for review”, „refuzat”)*, poate sugera reacții automate sau generarea de mesaje de avertizare. De asemenea, LLM-ul poate rezuma discuții lungi și oferi moderatorilor un motivaj concis pentru deciziile sale, ajutând la scalare. 

Importanța tehnologiei LLM în siguranță este ilustrată de exemple din industrie: se plasează Claude ca „un instrument specializat de moderare” care scapă de limitările filtrării bazate pe reguli simple. La ITU Online se arată că *Claude e eficient în gestionarea excepțiilor*: în loc de doar blocare de cuvinte cheie, el poate înțelege context, ton și intenție, reducând fals-pozitivele și fals-negativele. În plus, Claude (și competitorii săi) pot ajuta și în alte fluxuri de siguranță: generare de documentație de politici de securitate, analiză de jurnal (log) pentru comportamente anormale sau automatizarea unor sarcini repetitive de securitate internă. *Notă:* tehnologiile LLM trebuie folosite cu atenție la confidențialitatea datelor clienților și cu supraveghere umană acolo unde pot exista erori.  

În concluzie, cunoașterea conceptelor de bază despre LLM (ex. ChatGPT, Claude) și modul în care ele pot fi aplicate la **moderarea conținutului** (trust & safety) sau **analiza comportamentului utilizator** este un plus. Deși rolul e axat pe full-stack, o *„mentalitate AI”* înseamnă a fi conștient că se pot integra servicii cognitive în soluțiile de siguranță.
